## 슬라이드 3. 문제 정의 — 왜 필요한가

**화면 구성**
- 문제 1. 휘발성 데이터: 메신저 대화는 시간이 지나면 검색·복구가 어렵고, 결정했던 근거가 사라진다
- 문제 2. 분산된 외부 소스: 공유 문서·받은파일·서버 정보가 여러 곳에 흩어져 재사용이 어렵다
- 문제 3. 맥락 주입의 비효율: 매번 사람이 관련 맥락을 찾아 직접 붙여넣어야 하며, 누락·중복이 발생한다
- 강조 박스: 실제 Physical AI 프로젝트 개발 과정에서 이 문제를 직접 체감

**발표 스크립트**
> 프로젝트를 진행하다 보면 메신저로 논의하고, 문서를 공유받고, 파일을 전달받는 일이 매일 반복됩니다.
> 문제는 이 정보들이 시간이 지나면 메신저 대화창 저 아래로 묻히거나, 어느 폴더에 있었는지 기억이 안 나는 식으로 사실상 유실된다는 점입니다.
> 그래서 결정의 근거를 다시 찾으려면 사람이 채팅을 위로 스크롤하며 찾거나, 여러 폴더를 뒤져야 했습니다. 이 비효율을 직접 겪으면서, "이걸 구조화해서 저장하고 질의로 꺼내 쓰면 되지 않을까"라는 생각에서 이 프로젝트를 시작했습니다.

## 슬라이드 4. 배경지식 — 에이전트와 맥락(Context)

**화면 구성**
- AI 에이전트(Claude 등)는 맥락(Context)을 프롬프트로 받아야 정확하게 일할 수 있다
- 맥락 품질이 높을수록 → 결과 품질이 높아진다
- 하지만 맥락은 대화·문서·파일에 흩어져 있고, 사람이 매번 찾아서 복사-붙여넣기 해야 했다
- 비유 박스: "회의에 들어갈 때마다 브리핑 자료를 매번 새로 만드는 것과 같다. context-DB는 이미 정리된 브리핑 자료 창고를 만들어, 에이전트가 필요할 때 직접 꺼내가게 한다."

**발표 스크립트**
> 이 슬라이드는 Claude Code를 아직 익숙하게 다루지 못하시는 분들을 위한 부분입니다.
> AI 에이전트에게 일을 시킬 때 가장 중요한 게 "맥락", 즉 컨텍스트입니다. 같은 질문이라도 관련 배경 정보를 얼마나 정확하게 주느냐에 따라 결과물의 품질이 크게 달라집니다.
> 그런데 지금까지는 이 맥락을 사람이 매번 직접 찾아서 프롬프트에 붙여넣어야 했습니다. 이 작업 자체가 비효율이자 실수의 원인이었습니다.
> context-DB는 이 맥락 자체를 데이터베이스에 미리 정리해 두고, 에이전트가 필요한 순간에 스스로 질의해서 가져가게 만든 것이라고 이해해 주시면 됩니다.

## 슬라이드 5. 해결 방안 & 시스템 아키텍처

**화면 구성**
- 정의: context-DB = 흩어진 맥락을 정규화된 관계형 DB에 적재하고, 에이전트가 skill로 스스로 질의해 필요한 맥락만 회수하는 시스템
- 흐름도(좌→우 5단계 박스, 화살표로 연결):

```
원천 데이터           적재기              저장소              질의 인터페이스        에이전트
(메신저·웹 문서·   →   ingest.py     →   SQLite + FTS5   →   CLI / skill      →   맥락 소비
 받은파일)              (파서·정규화)
```

**발표 스크립트**
> 전체 그림은 이렇습니다. 왼쪽부터 순서대로 보면,
> 먼저 메신저 대화, 공유 문서, 받은 파일 같은 원천 데이터가 있습니다.
> 이걸 ingest.py 라는 적재기가 읽어서 파싱하고 정규화한 뒤 DB에 저장합니다.
> 저장소는 SQLite에 FTS5라는 전문검색 기능을 얹은 형태입니다.
> 그리고 이 DB 위에 CLI와 skill이라는 질의 인터페이스를 두어서, 마지막으로 에이전트가 이 인터페이스를 통해 필요한 맥락만 꺼내갑니다.
> 오늘 발표의 핵심은 가운데에 있는 저장소, 즉 DB를 어떻게 설계했는가이기 때문에 다음 슬라이드부터는 이 부분을 집중적으로 설명드리겠습니다.

## 슬라이드 6. DB 설계 — 정규화·관계·제약

**화면 구성**
- 관계도(3단):
  - `PROJECT → SOURCE ← SOURCE_TYPE`
  - `SOURCE → CONTEXT_ITEM ← PERSON`
  - `CONTEXT_ITEM → LINK`, `CONTEXT_ITEM ⇄ TAG (M:N, 접합 테이블 CONTEXT_ITEM_TAG)`
- 정규화(3NF): 반복되는 유형·작성자·태그를 별도 테이블로 분리해 중복 제거
- 1:N 관계: 프로젝트→소스→맥락항목, 인물→맥락항목
- M:N 관계: 맥락항목 ↔ 태그 (접합 테이블로 다대다 표현)
- 제약: `PK`/`FK`, `UNIQUE(source_type_id, name)`, `CHECK(is_ephemeral IN (0,1))` 로 무결성 보장

**발표 스크립트**
> 이번 과제의 핵심 파트인 DB 설계입니다.
> 가장 위에 프로젝트가 있고, 프로젝트 아래 여러 소스, 즉 메신저 채널이나 문서 저장소가 매달립니다. 그리고 각 소스 아래 실제 맥락 최소 단위인 context_item들이 쌓입니다.
> 소스 유형, 예를 들어 메신저인지 웹 문서인지 파일인지는 source_type이라는 별도의 조회 테이블로 분리해서, 같은 값이 반복 저장되지 않도록 정규화했습니다. 이게 3차 정규형의 핵심입니다.
> 그리고 태그는 맥락 항목과 다대다 관계이기 때문에, context_item_tag라는 접합 테이블을 따로 두어 표현했습니다.
> 마지막으로 외래키와 유니크, 체크 제약을 걸어서, 잘못된 값이 들어가거나 중복 등록되는 것을 DB 차원에서 막았습니다.

## 슬라이드 7. DB 핵심 기술 — FTS5 전문검색

**화면 구성**
- FTS5 가상 테이블(external content 방식): `context_item.content` 를 실시간 색인
  ```sql
  CREATE VIRTUAL TABLE context_fts USING fts5(
    content, content='context_item', content_rowid='context_item_id'
  );
  ```
- 트리거 3종으로 자동 동기화: `INSERT`/`UPDATE`/`DELETE` 시 FTS 색인이 항상 최신 상태 유지
- 인덱스 전략: `source_id`, `event_ts`, `person_id` — 소스별/시간순/인물별 조회 최적화
- 검색 예시: `context-db search "서버 권장사양"` → 관련 대화를 즉시 전문검색으로 회수

**발표 스크립트**
> 일반적인 LIKE 검색은 문자열을 처음부터 끝까지 훑기 때문에 데이터가 많아지면 느려지고, 정확한 어절 검색이 어렵습니다.
> 그래서 SQLite에 내장된 FTS5라는 전문검색 엔진을 사용했습니다. context_item 테이블의 내용을 별도의 가상 테이블에 색인해두고, 검색은 이 색인을 사용합니다.
> 중요한 점은, 원본 테이블에 새 대화가 들어오거나 수정, 삭제될 때마다 트리거가 자동으로 색인을 동기화해준다는 것입니다. 그래서 사람이 별도로 재색인할 필요가 없습니다.
> 여기에 소스별, 시간순, 인물별로 조회할 수 있도록 인덱스도 추가해서, "최근 대화부터", "이 사람이 한 말만" 같은 질의도 빠르게 처리되도록 했습니다.

## 슬라이드 8. Skill/CLI 연동 — 에이전트가 스스로 질의

**화면 구성**
- CLI 명령: `search` · `timeline` · `by-tag` · `by-person` · `links` · `stats` — 전부 `--json` 지원
- 읽기전용 강제: 조회 명령은 SELECT만 수행, 적재(쓰기)는 `ingest`/`watch` 로 경로를 하나로 통일
- skill 문서에 스키마 요약 + 파라미터화 질의 템플릿을 담아 에이전트가 스스로 숙지
- 강조 박스: 동작 흐름 — "이 작업의 맥락 줘" → skill이 알맞은 질의 템플릿 선택 → 파라미터만 채워 실행 → 결과(JSON)를 맥락으로 바로 사용
- 태그: 안전성 / 에이전트 친화(JSON) / 이식성

**발표 스크립트**
> DB에 직접 SQL을 날리는 방법도 검토했지만, 최종적으로는 CLI를 한 겹 두는 방식을 택했습니다.
> 이유는 세 가지입니다. 첫째, 조회는 읽기 전용으로 강제하고 쓰기는 ingest와 watch로만 하도록 경로를 하나로 묶어서 실수로 데이터가 훼손되는 걸 막을 수 있었습니다.
> 둘째, 에이전트 입장에서는 스키마나 SQL 문법을 몰라도, skill 문서에 있는 질의 템플릿에 파라미터만 채우면 되기 때문에 훨씬 다루기 쉽고, 결과도 JSON으로 표준화되어 있어 파싱이 쉽습니다.
> 셋째, 나중에 DB를 다른 엔진으로 옮기더라도 CLI 계약만 유지하면 되기 때문에 이식성도 좋습니다.
> 결과적으로 에이전트가 "이 작업 맥락을 줘"라고 하면, skill이 알맞은 명령을 골라 실행하고 그 결과를 그대로 맥락으로 사용하는 흐름이 완성됩니다.
