## Q1. FTS5 전문검색은 어디에, 어떻게 쓰였나? 한글 검색 품질은 보증되나?

**용도**: `context_item.content`(대화 본문)만 색인한다. `search`, `tag`(키워드로 대상 선정) 명령이 FTS5를 쓰고, `by-tag`/`by-person`/`timeline`은 일반 SQL(인덱스)만 쓴다.

```sql
CREATE VIRTUAL TABLE context_fts USING fts5(
  content, content='context_item', content_rowid='context_item_id'
);
```
`tokenize` 옵션을 지정하지 않아 FTS5 기본 토크나이저(**unicode61**)를 그대로 쓴다.

**한글 품질 — 보증 범위가 제한적이다.** 실측 검증(테스트보고서 §5b, PASS×2):
- ✅ 어절(띄어쓰기 단위) **완전일치**는 잘 된다 — `search "서버"` → "서버"가 독립 어절인 대화를 회수.
- ❌ **부분문자열은 매치 안 됨** — "안녕"으로 검색해도 "안녕하세요"는 안 걸림(형태소 분석·조사 처리가 없음).
- ✅ **접두어 검색(`키워드*`)은 됨** — "안녕*"이면 "안녕하세요"도 걸림.

즉 "정확한 단어 검색"은 되지만 "형태소 인식 검색"은 아니다. 알려진 한계로 문서화되어 있으며(ADR §7-1), 완화책은 접두어 검색 안내, 차기 확장으로 trigram 토크나이저나 의미(벡터) 검색을 검토 중이다.

## Q2. 태그의 역할은?

`tag` / `context_item_tag`(M:N 접합 테이블)로 구현되며, **소스·프로젝트 구조와 무관하게 대화·링크를 가로질러 묶는 수동 라벨**이다.

- 부여: `context-db tag "<키워드>" --add <태그명>` → FTS로 키워드 매치된 항목(최대 `--limit`)에 일괄 태깅, 또는 `--id`로 특정 항목 하나만 지정.
- 조회: `by-tag <태그>` → 태그가 붙은 모든 `context_item` + 연결된 `link`를 함께 반환(`v_tag_links` 뷰와 동일 로직).

용도는 "채널/프로젝트로는 안 묶이는 주제·결정 사항을 사람이 골라 모아두는 것"이다. 예: 여러 채널에 흩어진 "서버 스펙 논의"를 `서버스펙` 태그로 묶으면 채널을 넘나들며 한 번에 조회된다. **현재는 자동 태깅 없이 전부 수동**이다.

## Q3. 프로젝트/웹 소스 등이 수시로 늘어나는 건 어떻게 유지하나?

전부 **"없으면 자동 생성(upsert)"** 방식이라 스키마 변경이나 수동 등록이 필요 없다.

- **프로젝트**: `get_or_create_project()` — `INSERT OR IGNORE`로 이름 기준 자연키 upsert. `--project "신규프로젝트명"`으로 ingest 한 번 돌리면 즉시 새 프로젝트가 생긴다.
- **소스(채널/웹문서/파일함)**: `upsert_source()` — 자연키 `(source_type_id, name)` 기준. 채팅저장 폴더에 새 채널 폴더가 생기면 다음 `ingest`/`watch` 때 자동으로 새 SOURCE로 잡힌다.
- **상시 반영**: `watch --interval`(또는 스케줄러 등록)이 주기적으로 같은 루트를 재스캔하므로, 신규 채널·파일·문서가 생겨도 다음 주기에 자동 흡수된다.

## Q4. 작성자/소스/프로젝트 값이 없는 경우 — 저장·조회 시 누락되나?

핵심은 **"NULL이어도 조용히 누락시키지 않는다"** 는 설계다.

| 값 | NULL 허용? | 실제로 비는 경우 | 조회 시 처리 |
|---|---|---|---|
| **소스(source_id)** | ❌ 불가(NOT NULL) | 없음 — 모든 `context_item`은 반드시 소스에 속함 | 해당 없음 |
| **프로젝트(project_id)** | ❌ 불가(NOT NULL) | `--project` 미지정 시 기본값 `'미분류'`로 자동 귀속 | "미분류" 버킷으로 정상 조회됨(빠지지 않음) |
| **작성자(person_id)** | ✅ 허용(nullable FK) | 현재 메신저 파서는 헤더에 이름이 항상 있어 실질적으로 거의 없음. `note`/`excerpt` 같은 향후 항목 유형을 위해 열어둔 것 | `timeline`은 `LEFT JOIN person` → 작성자 없으면 그 필드만 `null`, 행은 그대로 회수됨. `by-person "이름"`은 `JOIN`(inner)이라 애초에 이름으로 찾는 질의라 작성자 없는 항목은 대상이 아님(의도된 동작) |
| **link title** | ✅ 허용(nullable) | 제목 없이 등록된 경우 | `null`로 표시, 행은 유지 |

검색·타임라인류(다수 조회)는 전부 `LEFT JOIN`이라 값이 비어서 결과에서 사라지는 일은 없다. `stats`의 `orphan_items` 지표로 고아 데이터(소스가 삭제됐는데 남은 항목)가 0인지도 상시 확인한다. 유일하게 "빠지는" 경우는 `by-person`처럼 애초에 그 값으로 필터링하는 질의뿐이며, 이는 누락이 아니라 정상적인 필터 동작이다.

## Q5. 향후 RDB를 벡터DB로 완전 교체할 계획인가, 부분 교체라면 어디를 바꾸나?

**결론: 전체 교체 계획은 없고, 부분(하이브리드) 확장이 설계 방향이다.**

- 정규화된 관계(프로젝트/소스/인물/태그/링크의 1:N·M:N, 무결성 제약)는 관계형 DB가 유리한 영역이라 그대로 유지한다. 벡터DB는 이런 구조적 관계·제약을 표현하는 데 적합하지 않다.
- 교체 후보는 **`context_item.content`의 검색 경로 하나뿐**이다 — 지금은 FTS5(정확·접두어 매칭)로 처리하는데, 이걸 임베딩 기반 유사도 검색(pgvector/FAISS 등)으로 **보완**해 "의미가 비슷한 대화 찾기"를 지원하는 것이 차기 계획이다(과제제안서 §7 "차기", ADR §7-1).
- 이식성도 이미 고려돼 있다: 스키마를 표준 SQL로 유지해, 필요하면 SQLite → PostgreSQL(+`tsvector`/`pgvector`)로 저장소 자체를 옮기는 것도 가능하도록 설계했다(상위설계서 §8 이식성).

한 줄 요약: **"구조(누가·어디서·무슨 프로젝트)는 RDB, 의미 검색(내용이 비슷한 걸 찾는 것)만 벡터로 보강"** 하는 하이브리드 방향이며, DB 전체를 벡터DB로 바꾸는 계획은 없다.

## Q6. `--help` 기능이 있나?

있다. `argparse` 기반이라 최상위 명령과 모든 하위 명령에 자동으로 `-h`/`--help`가 붙는다.

```bash
context-db --help              # 전체 명령 목록(14개, 각 한 줄 설명 포함)
context-db search --help       # search 명령의 인자(keyword, --project, --limit, --json)
context-db setup --help        # setup 명령의 옵션(--provider, --path, --background, --interval)
```
최초에는 각 옵션에 `help=` 문구가 비어 있어 이름만 나오는 상태였으나, 전체 명령·인자에 한글 설명을 채워 넣었다(2026-08-11).

## Q7. "미분류" 상태의 소스에 프로젝트를 지정하거나, 프로젝트명이 잘못 입력된 데이터를 어떻게 고치나?

**질문 시점(초기 구현)**: `set-project` 명령이 **메신저 채널에만 하드코딩**되어 있어 웹 문서·파일함 소스는 재매핑이 불가능했다. 이 제약을 없애고 두 가지 명령으로 정리했다(ADR-013).

**① `set-project` — 소스 타입 제약 제거**
```bash
context-db set-project "메신저 받은파일" "피지컬AI"            # 미분류 소스에 프로젝트 지정
context-db set-project "테스트문서" "피지컬AI" --type web_doc  # 이름이 여러 타입에 겹칠 때만 --type 필요
```
이름이 두 개 이상의 소스 타입에 동시에 존재하면 어느 쪽인지 모호하므로, `--type`을 요구하는 에러 메시지를 내고 자동으로 잘못 고르지 않는다.

**② `rename-project` — 프로젝트명 오타/오배정 수정 (신규 명령)**
```bash
context-db rename-project "피지컬 AI" "피지컬AI"        # 새 이름이 없으면: 단순 이름 변경
context-db rename-project "피지컬AI테스트" "피지컬AI"    # 새 이름이 이미 있으면: 그 프로젝트로 병합 후 빈 프로젝트 자동 삭제
```
`get_or_create_project`가 이름 기준 자연키라 오타는 곧 새 프로젝트로 취급된다. `rename-project`는 소속 소스를 전부 올바른 프로젝트로 옮기고 빈 프로젝트를 삭제해 오타로 쪼개진 프로젝트를 병합한다.

**검증**: 회귀 테스트 3건 추가(file 타입 재매핑, 단순 이름변경, 병합) — 전체 43/43 PASS.
