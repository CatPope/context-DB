# context-DB 접근 방식 비교 보고서 — DB 직접 접근 vs CLI 경유

| 구분 | 내용 |
|---|---|
| 문서 종류 | 기술 비교 보고서 |
| 작성일자 | 2026-08-10 |
| 대상 | context-DB(SQLite + FTS5)에서 맥락을 회수하는 두 방식 |
| 관련 문서 | `상위설계서.md`, `docs/context-db-상세설계서.md`, `context-db.skill.md` |

> **정의**
> - **DB 기반(직접 접근)**: 클라이언트(에이전트/사람)가 `sqlite3`로 `context.db`에 **직접 SQL**을 실행한다. 스키마·FTS 문법을 직접 다룬다.
> - **CLI 기반(경유)**: `context-db <command>`(→ `cli.py`)로 접근한다. 내부적으로는 같은 DB에 질의하지만, **미리 정의된 읽기전용 명령 + `--json`** 계약을 통해 접근한다.

---

## 1. 아키텍처 차이

```
[DB 기반]
  에이전트/사람 ──raw SQL──► sqlite3 드라이버 ──► context.db (스키마·FTS 직접 노출)
     (스키마 지식 필요, 쓰기 가능, PRAGMA 직접 관리)

[CLI 기반]
  에이전트/사람 ──명령+인자──► context-db(cli.py) ──검증·읽기전용──► context.db
     (스키마 은닉, 읽기전용 강제, --json 표준화, config로 경로 내재)
```

핵심은 **추상화 계층의 유무**다. CLI는 DB 위에 "안전한 읽기전용 계약"을 한 겹 둔다.

---

## 2. 항목별 비교표

| 항목 | DB 기반(직접 SQL) | CLI 기반(context-db) |
|---|---|---|
| **표현력/유연성** | ★★★★★ 임의 조인·집계·애드혹 질의 자유 | ★★☆ 정의된 명령만(search/timeline/by-tag/…) |
| **안전성(쓰기 사고)** | ★★ 실수로 `UPDATE/DELETE` 가능 | ★★★★★ 조회 명령은 읽기전용, 적재는 분리 |
| **학습 곡선/스키마 지식** | 필요(테이블·FK·FTS 문법 숙지) | 불필요(명령·인자만) |
| **에이전트 적합성** | ★★ 스키마 프롬프트 부담·오류 여지 | ★★★★★ 프롬프트 간결·`--json` 파싱 용이 |
| **오류 표면** | 큼(SQL 문법·컬럼명·PRAGMA 누락) | 작음(인자 검증·표준 출력) |
| **성능(단건)** | 빠름(프로세스 오버헤드 없음) | 매 호출 Python 기동 오버헤드(수십~수백 ms) |
| **성능(대량 반복)** | 유리(장기 커넥션 재사용) | 불리(호출마다 기동/커넥션) |
| **동시성(watch와 병행)** | 직접 쓰기 시 잠금 경합 위험 | 읽기 짧아 안전, 쓰기는 watch로 일원화 |
| **일관성/무결성** | 클라이언트마다 `PRAGMA foreign_keys=ON` 챙겨야 | CLI가 커넥션 규칙을 내부 보장 |
| **감사/로깅** | 분산(각 클라이언트) | 단일 지점(명령 계층에 로깅 삽입 용이) |
| **이식성/이관** | 경로·드라이버·SQL을 클라이언트가 의존 | 경로는 config 내재, 이관 시 내부만 교체 |
| **버전/계약 안정성** | 스키마 변경이 모든 클라이언트에 파급 | 명령 계약 유지 시 내부 스키마 자유 변경 |
| **확장(새 질의)** | 즉시(그냥 SQL 작성) | 코드 추가 필요(명령 구현) |

## 3. 장단점 요약

### DB 기반(직접 SQL)
- **장점**: 최고 유연성, 애드혹 심층 분석·일회성 통계에 즉시 대응, 계층 오버헤드 없음, 대량 반복 질의에 유리.
- **단점**: 스키마·FTS 지식 필수, **쓰기 사고 위험**, SQL 오류 여지, `PRAGMA` 등 규칙을 클라이언트가 책임, 스키마 변경에 취약, 감사·이식성 약함. 에이전트에게는 프롬프트 부담과 오류 확률이 크다.

### CLI 기반(context-db)
- **장점**: 스키마 은닉·**읽기전용 강제**로 안전, `--json` 표준 출력으로 에이전트 친화, 인자 검증으로 오류 최소화, 경로/규칙 내재로 이식성↑, **명령 계약**으로 내부 스키마를 자유롭게 진화(예: SQLite→PostgreSQL 이관 시 CLI 계약 유지), 로깅·감사 지점 단일화.
- **단점**: 정의된 명령 외 임의 질의 불가, 새 질의는 코드 추가 필요, 호출마다 프로세스 기동 오버헤드, 대량 반복엔 비효율.

## 4. 시나리오별 권장

| 상황 | 권장 | 이유 |
|---|---|---|
| 에이전트가 작업 맥락 회수 | **CLI** | 안전·`--json`·스키마 프롬프트 불필요 |
| 일상 검색/타임라인/태그 조회 | **CLI** | 표준 명령으로 충분, 실수 방지 |
| 백그라운드 지속 적재(쓰기) | **CLI**(`watch`/스케줄러) | 쓰기 경로 일원화로 무결성·멱등 보장 |
| 일회성 심층 분석·복잡 집계 | **DB 직접(읽기전용 커넥션)** | 임의 조인·통계가 필요하고 명령으로 표현 어려움 |
| 대량 배치 질의(수천 회) | **DB 직접(장기 커넥션)** | 프로세스 기동 오버헤드 회피 |
| 스키마/무결성 점검·마이그레이션 | **DB 직접** | DDL·PRAGMA·인덱스 직접 조작 필요 |

## 5. 결론 및 권고 — 하이브리드

- **기본값은 CLI 기반.** 에이전트 연동과 일상 조회·적재는 `context-db` 명령으로 통일한다. 안전성(읽기전용), 에이전트 친화(`--json`), 이식성(계약 안정)에서 우위이며, 이는 본 과제의 "에이전트가 skill로 스스로 질의" 목표와 정확히 일치한다.
- **DB 직접 접근은 예외적 도구로 유지.** 애드혹 심층 분석·대량 배치·마이그레이션처럼 CLI 명령으로 표현하기 어렵거나 오버헤드가 문제되는 경우에 한해, **읽기전용 커넥션**(예: `PRAGMA query_only=ON`)으로 사용한다.
- **쓰기는 항상 단일 경로.** 적재/수정은 `ingest`/`watch`(CLI)로만 수행해 멱등·무결성·동시성을 보장하고, 직접 쓰기는 지양한다.
- **동시성 보강 권장.** watch가 상시 쓰는 환경이므로 `PRAGMA journal_mode=WAL`을 적용하면 읽기(직접/CLI)와 쓰기(watch)의 경합이 크게 줄어든다.

> 요약: **"안전·표준·에이전트용"은 CLI, "유연·심층·대량"은 DB 직접.** 두 방식은 대체재가 아니라 역할 분담이며, CLI를 1차 인터페이스로 두고 DB 직접은 관리자/분석용 백도어로 남기는 하이브리드가 최적이다.
