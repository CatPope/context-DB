# context-DB 스키마 설명서

| 구분 | 내용 |
|---|---|
| 문서 종류 | 스키마 레퍼런스 (전체 테이블/뷰 설명) |
| 작성일자 | 2026-08-11 (2026-08-27 정규화 리팩터 반영) |
| 대상 | `src/schema.sql` 에 정의된 모든 테이블·가상 테이블(FTS5)·뷰 |
| 관련 문서 | `context-db-상세설계서.md`, `ADR-context-DB.md`, `질의응답.md`, `context-db-erd.mmd`(ERD) |

> DBeaver 등으로 DB를 직접 열어봤을 때 "이 테이블이 뭐 하는 거지?"에 바로 답하기 위한 문서다.
> 기본 테이블 9개 + FTS5 가상 테이블 1개(+ 내부 섀도 테이블 4개) + 뷰 3개로 구성된다.
>
> **참조 액션 주의**: 아래 FK의 `CASCADE`/`SET NULL`/`RESTRICT` 는 접속한 클라이언트가
> `PRAGMA foreign_keys = ON` 을 켰을 때만 발동한다. DBeaver 등 DB 브라우저는 기본적으로 켜지
> 않으므로, 직접 접속해 삭제할 때는 이 문서의 동작이 그대로 재현되지 않을 수 있다.
> 애플리케이션 경로(`src/db.py`의 `connect()`)는 항상 켠다.

## 1. 기본 테이블 (9개)

### 1.1 `project` — 최상위 분류
맥락이 속하는 프로젝트(예: "피지컬AI", "미분류"). 모든 소스는 반드시 프로젝트 하나에 속한다.

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `project_id` | INTEGER | PK | |
| `name` | TEXT | NOT NULL, UNIQUE | 자연키. 오타 시 `rename-project`로 병합/수정 |
| `description` | TEXT | | |
| `created_at` | DATETIME | DEFAULT now | |

**설계 이유**: 채널·문서·파일함을 프로젝트 단위로 묶어 조회 범위를 좁히기 위함(`search --project`, `timeline --project`). `--project` 미지정 시 자동으로 `'미분류'`에 귀속되어 데이터가 누락되지 않는다.

---

### 1.2 `source_type` — 소스 유형 조회 테이블
`messenger`/`web_doc`/`web_link`/`paper`/`server_info`/`file`/`note` 같은 유형 코드와 한글 라벨을 담는다.

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `source_type_id` | INTEGER | PK | |
| `code` | TEXT | NOT NULL, UNIQUE | 영문 코드(프로그램이 사용) |
| `label` | TEXT | NOT NULL | 한글 표시명(사람이 봄) |
| `is_ephemeral` | INTEGER | NOT NULL, DEFAULT 0, CHECK IN (0,1) | 휘발성 여부(`messenger`=1, 나머지 0) |

**설계 이유**: `source.source_type_id`에 문자열을 직접 반복 저장하지 않고 별도 조회 테이블로 분리(3NF 정규화). 새 유형이 늘어나도 시드 데이터만 추가하면 되고, 코드/라벨 변경(예: `google_doc`→`web_doc`)이 한 곳에서 끝난다.

`is_ephemeral`이 여기 있는 이유: 휘발성은 소스 하나하나의 성질이 아니라 **소스 유형이 결정하는 값**이다. `source`에 두면 `source_type_id → is_ephemeral` 이행 종속이 생겨 3NF를 위반하고, 실제로 적재 호출부마다 값을 손으로 넘겨야 했다.

**이 값이 적재 깊이를 가른다 (ADR-017)** — 이 DB 의 핵심 설계 원칙이다.

| `is_ephemeral` | 소스 유형 | 적재 깊이 | 근거 |
|---|---|---|---|
| `1` | `messenger` | **본문까지** `context_item` 으로 | 원본이 약 1개월 후 사라진다. 지금 안 담으면 영원히 못 담는다 |
| `0` | 나머지 6종 | `link` 로 **접근 경로만** | 원본이 그대로 있으므로 사본을 둘 이유가 없다 |

즉 이 DB 는 "모든 것의 사본"이 아니라 **"사라지는 것의 유일한 사본 + 남아있는 것으로 가는 길"** 이다. `web_doc`/`file` 소스에 `context_item` 이 없는 것은 결함이 아니라 설계다.

실측(2026-08-27): 전체 맥락 833건 중 **275건(33%)이 이미 원본 로그에서 사라져 이 DB 가 유일한 사본**이다.

### 1.3 `source` — 맥락의 출처 (채널/문서/파일함)
메신저 채널 1개, 웹 문서 1개, 받은파일 폴더 1개가 각각 `source` 행 1개다. **"채널이란?"** 질문의 답이 바로 이 테이블.

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `source_id` | INTEGER | PK | |
| `project_id` | INTEGER | NOT NULL, FK→project (UPDATE CASCADE / DELETE RESTRICT) | 가변 속성(재매핑 가능, `set-project`) |
| `source_type_id` | INTEGER | NOT NULL, FK→source_type (UPDATE CASCADE / DELETE RESTRICT) | |
| `name` | TEXT | NOT NULL | 채널명/문서제목/파일함명 |
| `uri` | TEXT | | **루트 토큰 표기**(아래 참조) 또는 웹 URL |
| `created_at` | DATETIME | DEFAULT now | |
| | | UNIQUE(`source_type_id`, `name`) | 자연키 — 멱등 적재의 핵심 |

**경로는 루트 토큰으로 저장한다**: `C:/Users/me/채팅저장/AI팀` 같은 머신 고유 절대경로 대신
`{chat_root}/AI팀` 으로 저장한다. 웹 URL(스킴이 있는 값)은 그대로 둔다.

| 저장 값 | 의미 |
|---|---|
| `{chat_root}/<채널명>` | 메신저 소스 폴더 |
| `{files_root}` | 받은파일 폴더 자체 |
| `{files_root}/<파일명>` | 받은파일 링크(`link.url`) |
| `https://...` | 웹 문서/링크 — 토큰화하지 않음 |

이유는 **DB 이식성**이다. 절대경로를 박아두면 DB 파일을 다른 PC 로 옮기는 순간 모든 경로가
죽는다. 토큰으로 두면 그 PC 의 `context-db.config.json` 값으로 해소된다.
해소·역변환은 `src/db.py` 의 `resolve_path()`/`pack_path()` 가 담당하며, CLI 조회는 출력 직전에
해소하므로 `--json` 의 `url` 필드는 종전대로 절대경로를 반환한다.
config 에 해당 루트가 없으면 토큰을 그대로 노출한다 — 조용히 빈 값으로 만들면 "루트 미설정"과
"파일이 최상위에 있음"을 구분할 수 없기 때문이다.

**설계 이유**: 자연키를 `(source_type_id, name)`으로 잡아서(ADR-002), 채널을 다른 프로젝트로 재매핑해도 재적재 시 새 소스가 중복 생성되지 않는다. `project_id`는 "정체성"이 아니라 "가변 속성"으로 취급한 게 핵심 설계 결정.

### 1.4 `item_type` — 맥락 항목 유형 조회 테이블
`message`/`note`/`excerpt`/`system`/`file`. `source_type`과 **성격이 같은 enum이므로 같은 방식(조회 테이블)으로 모델링**한다.

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `item_type_id` | INTEGER | PK | 시드에서 id를 명시적으로 고정(1~5) |
| `code` | TEXT | NOT NULL, UNIQUE | 영문 코드 |
| `label` | TEXT | NOT NULL | 한글 표시명 |

시드: `1=message` `2=note` `3=excerpt` `4=system` `5=file`

**id를 고정하는 이유**: `context_item.item_type_id`의 `DEFAULT 1`이 `message`를 가리킨다. auto rowid 배정에 맡기면 시드 순서가 바뀌는 순간 기본값이 엉뚱한 유형을 가리키게 된다.

**설계 이유**: 이전에는 `context_item.item_type`이 `CHECK IN (...)`으로 묶인 TEXT 컬럼이었다. 같은 성격의 `source_type`은 조회 테이블인데 이것만 CHECK enum이라 **같은 개념을 두 방식으로 모델링**하고 있었다. 유형을 추가하려면 DDL을 고쳐야 했고, 한글 라벨을 붙일 자리도 없었다.

### 1.6 `context_item` — 맥락의 최소 단위 (핵심 테이블)
대화 1건·메모·발췌 등 **실제 콘텐츠를 담는 본체**. 전문검색(FTS) 대상이 되는 유일한 테이블.

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `context_item_id` | INTEGER | PK | |
| `source_id` | INTEGER | NOT NULL, FK→source (UPDATE CASCADE / DELETE RESTRICT) | 어느 채널/소스의 항목인지 |
| `person_id` | INTEGER | FK→person (nullable, DELETE SET NULL) | 작성자 없어도 저장 가능. 발화자를 지워도 맥락은 남는다 |
| `item_type_id` | INTEGER | NOT NULL, DEFAULT 1, FK→item_type | 시스템알림/첨부파일라인도 구분. `1`=message |
| `event_ts` | DATETIME | | 실제 발화 시각 |
| `content` | TEXT | NOT NULL | 본문(FTS 색인 대상) |
| `external_id` | TEXT | **NOT NULL** | 멱등 dedup용 해시(sha1) |
| `created_at` | DATETIME | DEFAULT now | 적재된 시각(발화 시각과 다름) |
| | | UNIQUE(`source_id`, `external_id`) | 재적재해도 중복 안 생기는 핵심 키 |

**설계 이유**: `external_id = sha1(채널|시각|발화자|내용)`으로 자연 dedup 키를 만들어(ADR-005) 멱등 적재를 구현. `person_id`를 nullable로 열어둔 건 향후 작성자 없는 노트/발췌 항목도 같은 테이블에 담기 위함.

**`external_id`가 NOT NULL인 이유**: SQLite는 UNIQUE 제약에서 NULL을 서로 다른 값으로 취급한다. nullable이면 `UNIQUE(source_id, external_id)`가 무력화되어, `external_id`를 채우지 않는 적재 경로가 하나라도 생기는 순간 중복 방지가 조용히 무너진다.

**`thread_key`가 없는 이유**: 예전에는 `"채널명|날짜"` 형태의 컬럼이 있었다. 한 컬럼에 두 값을 패킹한 1NF 위반인 데다, 채널은 이미 `source_id`가, 날짜는 이미 `event_ts`가 결정하므로 중복이었다. 스레드는 이제 `(source_id, date(event_ts))`로 식별한다(`queries.sql` Q4).

**삽입 시 `INSERT OR IGNORE`를 쓰지 않는다**: `OR IGNORE`는 UNIQUE뿐 아니라 NOT NULL·CHECK 위반까지 삼켜서 제약 위반 행을 조용히 버린다. 적재기는 `ON CONFLICT(source_id, external_id) DO NOTHING`으로 충돌 대상을 명시해, 중복만 무시하고 나머지 제약 위반은 예외로 올린다.

### 1.7 `link` — 외부 자원(URL/파일 경로)
웹 문서 URL, 받은파일 경로 등. 앞서 설명한 대로 `context_item` 또는 `source`에 붙을 수 있는 **별도 테이블**.

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `link_id` | INTEGER | PK | |
| `context_item_id` | INTEGER | FK→context_item (nullable, DELETE CASCADE) | 대화 속 언급 링크면 여기 |
| `source_id` | INTEGER | FK→source (nullable, DELETE CASCADE) | 소스 자체에 붙는 링크(받은파일 등)면 여기 |
| `url` | TEXT | NOT NULL | `source.uri` 와 같은 루트 토큰 표기 또는 웹 URL |
| `title` | TEXT | | |
| `last_checked_at` | DATETIME | | 향후 dead-link 점검용 |
| | | CHECK((`context_item_id` IS NULL) `<>` (`source_id` IS NULL)) | **정확히 한쪽**에만 귀속(배타적 아크) |
| | | UNIQUE(`context_item_id`, `url`) WHERE `context_item_id` IS NOT NULL | 부분 유니크 인덱스 `ux_link_item` |
| | | UNIQUE(`source_id`, `url`) WHERE `source_id` IS NOT NULL | 부분 유니크 인덱스 `ux_link_source` |

**부분 유니크 인덱스인 이유**: 배타적 아크는 단일 UNIQUE로 표현할 수 없다(한쪽이 항상 NULL이고 SQLite는 NULL을 distinct 취급). 그래서 중복 판정을 오랫동안 적재기가 `IFNULL(...,-1)` 비교로 흉내내고 있었다. 아크별 부분 인덱스 2개로 나누면 DB가 직접 강제한다.

> 부분 인덱스를 `ON CONFLICT` 대상으로 지정할 때는 인덱스의 `WHERE` 절까지 함께 적어야 SQLite가 매칭한다. 생략하면 `ON CONFLICT clause does not match any PRIMARY KEY or UNIQUE constraint` 로 실패한다.

## 2. 전문검색(FTS5) — 가상 테이블 1개 + 섀도 테이블 4개

스키마에 직접 선언한 건 `context_fts` 하나뿐이고, 나머지 4개는 SQLite가 자동 생성하는 내부 구현체다(DBeaver에서 보이지만 직접 다루지 않음).

| 테이블 | 역할 |
|---|---|
| `context_fts` | 우리가 `MATCH`로 질의하는 가상 테이블. `content='context_item'` **external content 모드**라 원문을 복사하지 않고 `context_item.content`를 그대로 참조 |
| `context_fts_data` | 역색인(inverted index)의 실제 데이터(압축 세그먼트) |
| `context_fts_idx` | `_data` 세그먼트를 빠르게 찾기 위한 내부 색인 |
| `context_fts_docsize` | 문서(행)별 토큰 수 — 랭킹(`ORDER BY rank`) 계산에 사용 |
| `context_fts_config` | FTS5 인덱스 설정값(버전, 평균 문서 길이 등) |

**동기화**: `context_item`에 대한 `INSERT`/`UPDATE`/`DELETE` 트리거 3종이 `context_fts`에 자동 반영한다(수동 재색인 불필요). 한글 검색 특성(어절 단위 매칭, 부분문자열 미지원)은 `질의응답.md` Q1 참고.

## 3. 뷰 (3개) — 자주 쓰는 조인을 미리 정의

| 뷰 | 정의 | 용도 |
|---|---|---|
| `v_project_sources` | `source ⋈ project ⋈ source_type` | 프로젝트별 소스 요약 |
| `v_recent_context` | `context_item ⋈ source ⋈ project`, `LEFT JOIN person` | 전체 최근 맥락(작성자 포함), 최신순 |
| `v_tag_links` | `tag ⋈ context_item_tag ⋈ context_item`, `LEFT JOIN link` | 태그별 맥락+링크 |

뷰는 읽기전용 편의 창구이며, CLI(`cli.py`)는 대부분 뷰를 거치지 않고 동등한 JOIN을 직접 실행한다(뷰는 DB 직접 접근·애드혹 분석용).

## 4. 테이블 관계 한눈에 보기

```
PROJECT       ──1:N──▶ SOURCE ◀──1:N── SOURCE_TYPE
SOURCE        ──1:N──▶ CONTEXT_ITEM ◀──0:N── PERSON (nullable)
ITEM_TYPE     ──1:N──▶ CONTEXT_ITEM
SOURCE        ──0:N──▶ LINK ◀──0:N── CONTEXT_ITEM   (link은 둘 중 하나에만 귀속)
CONTEXT_ITEM  ──M:N──▶ TAG   (접합 테이블: CONTEXT_ITEM_TAG)
CONTEXT_ITEM  ──1:1(가상)──▶ CONTEXT_FTS  (외부 콘텐츠 FTS, 트리거로 동기화)
```

전체 크로우풋 ERD: `docs/dev/context-db-erd.mmd` (Mermaid 원본 — 이 문서와 함께 갱신한다)

## 5. 스키마 버전 관리

`schema.sql` 마지막 줄이 `PRAGMA user_version` 으로 스키마 버전을 찍고, `src/db.py`의
`SCHEMA_VERSION` 이 같은 값을 들고 있다. **스키마를 구조적으로 바꿀 때는 반드시 둘을 함께 올린다.**

`src/db.py`의 `connect()` 는 연결할 때마다 두 값을 대조해서, 낡은 스키마의 DB라면 첫 INSERT가
아니라 **연결 시점에** `SchemaVersionError` 로 실패시킨다. 조용히 잘못된 결과를 내는 것보다
명시적으로 막는 편이 낫기 때문이다. 이 경우 DB를 재구축해야 한다:

```
del context.db  &&  context-db init  &&  context-db ingest
```

> **재구축 시 주의**: 재적재로 복원되지 않는 데이터가 있다. `project` 배정(`set-project`),
> `tag`/`context_item_tag`(`tag` 명령), 그리고 **원본 파일이 이미 삭제된 `link` 행**은
> 원본 로그에서 재생성되지 않는다. 재구축 전에 따로 덤프해 두고 이후 복원해야 한다.
