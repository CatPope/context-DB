# context-DB 상위 설계서

| 구분 | 내용 |
|---|---|
| 과제명 | context-DB — 에이전트 맥락 저장·질의 데이터베이스 |
| 문서 종류 | 상위 설계서(High-Level Design) |
| 작성일자 | 2026-08-07 |
| DB | SQLite 3 + FTS5 (관계형, 순수 SQL) |
| 관련 문서 | `과제제안서.md` |

> 단기 개발 전제. MVP 범위의 **핵심 스키마 + 대표 질의 + skill 연동**까지만 설계하고, 벡터검색·UI·크롤링은 차기로 분리한다.

---

## 1. 목적

흩어지고 휘발되는 맥락(하이웍스 대화·외부 링크·문서)을 정규화된 관계형 스키마에 적재하고, 에이전트가 skill로 스키마를 숙지해 SQL/FTS로 필요한 맥락만 질의·회수하도록 하는 시스템의 상위 구조를 정의한다.

## 2. 시스템 아키텍처

```
[원천 데이터]            [적재]              [저장소]            [질의 인터페이스]        [소비]
하이웍스 로그(.txt)  ─►  ingest.py     ─►   context-DB      ◄─  query 템플릿(SQL/FTS) ◄─  에이전트
외부 링크/문서/논문       (파서·정규화)       (SQLite + FTS5)      (skill이 스키마 숙지)      (맥락 주입)
서버 정보/메모
```

- **적재기(ingest.py)**: 원천을 파싱해 `source`/`context_item`/`link`/`tag`로 정규화 저장.
- **저장소(SQLite)**: 정규화 스키마 + FTS5 인덱스.
- **질의 인터페이스**: 파라미터화된 SQL/뷰 모음. 에이전트는 **skill 문서**로 스키마와 질의법을 안다.
- **소비(에이전트)**: 질의 결과(맥락)를 받아 작업에 활용.

## 3. 데이터 모델 (ER)

> 이 절이 담고 있던 ERD(다이어그램 + 필드 목록)는 실행 가능한 산출물인 `src/schema.sql` 과
> 중복되어 스키마가 바뀔 때마다 그림이 따로 놀 위험이 있었다. **정본 스키마는 `src/schema.sql`
> 하나뿐**이며, 사람이 읽는 ERD·상세 설명은 `docs/dev/스키마-설명서.md` 를 참조한다.
> 아래 3.1~3.2 는 엔티티의 역할과 관계를 설명하는 서술로, 컬럼 단위 정의는 담지 않는다.

### 3.1 엔티티 정의
- **PROJECT**: 맥락이 속한 프로젝트(예: Physical AI). 최상위 분류.
- **SOURCE_TYPE**(조회): 소스 유형 코드(messenger, google_doc, web_link, paper, server_info, file, note).
- **SOURCE**: 맥락의 출처(메신저 채널, 문서, 링크 등). `is_ephemeral`로 휘발성 여부 표시.
- **PERSON**: 대화 작성자(메신저 발화자). 작성자 없는 항목은 NULL.
- **CONTEXT_ITEM**: 맥락의 최소 단위(대화 1건·메모·문서 발췌). 시간(`event_ts`)·내용(`content`) 보유. 전문검색 대상.
- **LINK**: 외부 자원 URL. 맥락 항목에 첨부되거나 소스 단독으로 존재.
- **TAG** / **CONTEXT_ITEM_TAG**: 태그와 M:N 접합(다대다).

### 3.2 관계 요약
- 1:N — PROJECT→SOURCE, SOURCE_TYPE→SOURCE, SOURCE→CONTEXT_ITEM, PERSON→CONTEXT_ITEM, (SOURCE·CONTEXT_ITEM)→LINK
- **M:N** — CONTEXT_ITEM ↔ TAG (접합 테이블 CONTEXT_ITEM_TAG)
- 정규화: 반복되는 유형/작성자/태그를 별도 테이블로 분리(3NF).

## 4. 논리 스키마

이 절이 담고 있던 DDL 발췌는 `src/schema.sql`(정본) 및 `docs/dev/스키마-설명서.md`(사람이 읽는
설명)와 중복되므로 제거했다. 테이블·제약·인덱스의 정확한 정의는 두 문서를 참조한다.

## 5. 주요 질의·인터페이스 (대표)

```sql
-- Q1. 프로젝트의 최근 맥락 N건(타임라인)
SELECT ci.event_ts, p.display_name, ci.content
FROM context_item ci
JOIN source s   ON s.source_id = ci.source_id
LEFT JOIN person p ON p.person_id = ci.person_id
WHERE s.project_id = :project_id
ORDER BY ci.event_ts DESC
LIMIT :n;

-- Q2. 키워드 전문검색(FTS)
SELECT ci.event_ts, ci.content
FROM context_fts f
JOIN context_item ci ON ci.context_item_id = f.rowid
WHERE context_fts MATCH :keyword
ORDER BY ci.event_ts DESC;

-- Q3. 태그로 맥락+링크 조회 (M:N + LINK)
SELECT ci.content, l.url
FROM context_item ci
JOIN context_item_tag t ON t.context_item_id = ci.context_item_id
JOIN tag g ON g.tag_id = t.tag_id
LEFT JOIN link l ON l.context_item_id = ci.context_item_id
WHERE g.name = :tag;
```

뷰(`v_project_sources` 등 3종)는 `src/schema.sql` 이 정본이다. 이 절의 Q1~Q3는 대표 질의의
설계 의도를 남긴 것으로, 정확한 조인·조회 경로는 `src/queries.sql`/`src/cli.py`를 참조한다.

## 6. Skills 연동 설계 (핵심)

- **skill 문서**(`context-db.skill.md`)에 다음을 담아 에이전트가 스키마를 숙지하게 한다:
  1. **스키마 요약**(표 목록·주요 컬럼·관계) — 위 §3~4 축약본.
  2. **질의 템플릿**(§5의 파라미터화 SQL). 에이전트는 파라미터만 채워 실행.
  3. **사용 규칙**: 읽기 전용(SELECT) 우선, 결과 행수 제한(LIMIT), 프로젝트 범위 지정 권장.
- **동작 흐름**: 에이전트가 "이 작업의 맥락 줘" → skill의 질의 템플릿 선택 → 파라미터 채워 SQLite 질의 → 결과(맥락)를 컨텍스트로 사용.
- (선택 2차) 질의 이력 `query_log`에 남겨 자주 쓰는 맥락을 분석.

## 7. 데이터 적재 흐름 (ingest.py)

1. 하이웍스 로그(`날짜.txt`) 파싱 → `[시각] 이름` 패턴 추출 → `person` 확보 → `context_item`(item_type=message) INSERT.
2. 채널/문서/링크는 `source`(+`source_type`) 등록, URL은 `link`.
3. 태그는 키워드 규칙 또는 수동 지정 → `context_item_tag`.
4. INSERT 후 트리거/배치로 `context_fts` 동기화.

## 8. 비기능 요구

- **성능**: 조회 컬럼 인덱스 + FTS5. 단일 파일 DB로 수만~수십만 행 대응.
- **무결성**: FK·UNIQUE·CHECK. 적재는 트랜잭션 처리(중복 `external_id` 무시/갱신). ※ SQLite는 FK가 기본 비활성이므로 커넥션마다 `PRAGMA foreign_keys=ON` 필수(검증 완료).
- **프라이버시**: 사내 대화 포함 → 로컬 파일 저장, 외부 전송 금지. 백업 = DB 파일 복사.
- **이식성**: 표준 SQL 유지 → 추후 PostgreSQL(+tsvector) 이관 가능.

## 9. 향후 확장 (차기)

- 의미(벡터) 검색: 임베딩 + 유사도(pgvector/FAISS)로 "의미 기반 맥락 회수".
- 자동 수집·증분 적재, 웹 UI, 접근권한/멀티유저, 결정(decision) 엔티티로 근거 추적 강화.

| 위험 | 대응 |
