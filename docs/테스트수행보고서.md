## 1. 요약

- 테스트계획서 §5의 항목(A 수집충실성 · B 검색 · C 에이전트회수 · D 무결성/운영 · E 비기능)을 실제 수행하고 **전건 통과**를 확인함.
- 검증 방식: **자동화 스위트**(격리 합성데이터) + **skill 기반 시나리오**(운영 `context.db` 610건, 읽기전용) + **운영 생애주기**(임시 DB 격리).
- 기존 수집 방식(하이웍스 채널·받은파일·구글독스)을 그대로 적재·회수하여, 브리핑 워크플로우가 context-DB로 재현됨을 확인함.

## 2. 시험 환경

- Windows 11 / Python 3.13 (내장 SQLite **FTS5 포함**) / 표준 라이브러리만.
- 운영 `context.db` 는 읽기전용 조회에만 사용, 쓰기 시험은 임시 DB(`--db <tmp>`)로 격리(운영 데이터 불변).

## 3. 수행 방법

1. 자동화: `PYTHONPATH=<repo> python tests/test_context_db.py`
2. skill 시나리오: 운영 DB에 `search/timeline/by-person/links/... --json`
3. 운영 생애주기: 임시 DB에 `init → ingest → 재ingest → set-project → tag`

## 7. 발견 및 한계

1. **한국어 FTS 토큰 매칭**: 부분문자열 미매치(조사·붙임). 완화 — 접두어 `키워드*`·정확구문, 차기 트라이그램/의미검색. (버그 아님, 설계상 한계)
2. **동일 분 반복 발화 병합**: 현 구현 dedup 키에 라인순번 미포함 → 같은 분 동일 발화 4건이 1건으로 병합(관측). 필요 시 `line_no` 포함(설계 패치안 존재).
3. **설계서(M:N) vs 구현(1:N) 불일치**: `set-project` 가 `UPDATE source.project_id`(1:N)로 동작. 프로젝트 매핑 모델 일원화 결정 필요(별도 이슈).
